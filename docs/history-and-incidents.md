# trio-sync — история и разбор инцидентов

Подробная версия хронологии из `HANDOFF.md`, с разбором каждого инцидента — что произошло, что подумали, что оказалось правдой, и какое правило протокола из этого выросло. Полезно, если непонятно, *почему* правило именно такое, а не просто *какое* оно.

## v0.1 — рождение протокола (29.07, ночь)

Cowork, работая внутри Claude-проекта Finanon, замечает и формулирует проблему: chat/Code/Cowork не делятся контекстом на одном и том же проекте. Проектирует минимальный файловый протокол — `.trio/STATUS.md` + `.trio/LEDGER.md` — и сразу же наполняет `STATUS.md` реальным состоянием Finanon (Фаза 5: PDF-импорт выписки, ручная категоризация; сквозные требования NFR-4, NFR-11, спецификация §7), а не оставляет пустым. Доставляет плагин и стартовую папку.

**Урок:** протокол работает только если все три поверхности реально его используют — весь следующий день ушёл на подтверждение, что Code и Cowork оба реально читают/пишут файлы, а не просто установили скилл.

## v0.2 — зеркалирование для Chat (29.07, вечер)

Обычный Chat, в отличие от Code и Cowork, не имеет доступа к файлам ни при каких настройках — это не вопрос прав, а архитектурное ограничение продукта. Единственный автоматический канал для Chat — документы прикреплённого Claude Project. Cowork добавляет шаг: после реальной работы над `STATUS.md` — писать зеркало-снэпшот в проект (`claude/trio-status-snapshot.md`).

Заодно: генерализация протокола как привычки на все будущие проекты пользователя (не только Finanon) — зафиксировано в персональной памяти Claude на стороне пользователя. Также — уборка рабочей папки: файлы без места в git-репозитории скопированы в `reference/`, устаревшие черновики помечены на удаление (Cowork может копировать, но не может удалять файлы на машине пользователя).

## Побочная ветка: gist-канал, заведённый и отменённый в один день

В тот же вечер пользователь напрямую (в обход Cowork) договорился с Code о дополнительном канале: после значимой работы Code дублирует короткую заметку в приватный gist (`code-note.md`), который потом читает Chat.

Через несколько часов Cowork, разбирая `.trio/` перед очередной задачей, обнаруживает: реальная находка Code в тот вечер (незалогированный acceptance-review, 2 бага) существовала только в переписке с пользователем — **не попала в `.trio/LEDGER.md`** вообще, хотя это единственный обязательный канал. При этом gist, судя по всему, не помог — проблема была не в отсутствии второго канала, а в том, что первый (обязательный) не был соблюдён.

**Решение Cowork (согласовано с пользователем в ту же ночь):** отменить gist-канал. Обоснование: второй канал, который сам Cowork не может проверить (нет доступа к GitHub gist), увеличивает риск тихого расхождения, а не снижает его — особенно когда единственный по-настоящему обязательный канал и так иногда пропускается. Cowork переписывает `CLAUDE.md`: убирает инструкцию про gist, оставляет явную пометку «это отменено» (на случай если старый контекст/память всплывёт снова), усиливает правило «ответ пользователю не считается выполненным, пока не залогировано в `.trio/LEDGER.md`», добавляет канарейку — строку `ToЕьмат` в конец файла, чтобы можно было попросить Code процитировать её и убедиться, что Code реально прочитал свежий файл, а не работает по устаревшему контексту.

**Урок, который лёг в основу v0.3.0:** не добавлять непроверяемые каналы поверх ненадёжно соблюдаемого обязательного — вместо этого сделать обязательный канал удобнее и понятнее (см. TO_CODE/FROM_CODE ниже).

**Постскриптум, обнаруженный 30.07 при прямой проверке файла:** канарейка `ToЕьмат` в реальном `CLAUDE.md` так и не появилась — файл заканчивается строкой «Секретное слово: Зануда», без всякого `ToЕьмат`. То есть даже запись про добавление защитного механизма против рассинхрона сама разошлась с диском. Не исправлено умышленно — оставлено как живой пример того, что LEDGER надо перепроверять, а не читать как абсолютную истину.

## v0.3.0 — направленные инбоксы и «хот-память» (30.07)

В отдельном разговоре с пользователем внутри проекта Finanon, Cowork строит полную картину протокола по явной просьбе — и получает два новых требования:

1. **Строгое разделение направления.** Пользователь приводит пример: должен быть «отдельный файл, который Code читает с промптом, и отдельный файл, где читается его ответ» — вместо текстового поля `Handoff:` внутри общей записи LEDGER, из-за которого непонятно, что именно адресовано лично тебе, без просеивания всей истории.
2. **Постоянная «хот-память».** Пользователь хочет, чтобы переписка с Code сохранялась и не чистилась, пока он сам не попросит — чтобы можно было быстро вернуться к ней, не поднимая заново текущий контекст разговора. Ни `STATUS.md` (перезаписывается), ни `LEDGER.md` (обязан быть кратким по правилу) для этого не годятся.

Cowork предлагает два варианта на (1) — минимальная конвенция внутри LEDGER, или отдельные файлы — и явно не создаёт файлы, пока пользователь не подтвердит, поскольку это меняет протокол, которым пользуется и Code. Пользователь подтверждает: отдельные файлы (`TO_CODE.md`/`FROM_CODE.md`), `DIALOGUE.md` для хот-памяти, и — закрепить всё это в самом плагине (не разовая надстройка на один проект).

Cowork выпускает v0.3.0: обновляет `SKILL.md`/`README.md`/`plugin.json` плагина, добавляет явное предупреждение «`CLAUDE.md` — никогда не канал хендоффа» (см. следующий раздел), упаковывает и доставляет `.plugin`-файл.

## Гипотеза «Code писал в CLAUDE.md» — проверена и не подтвердилась

При обсуждении v0.3.0 пользователь предположил, что причиной старой (ещё до gist-эпизода) нестыковки — когда Cowork не видел обновления `.trio/`, которые Code утверждал, что закоммитил, — было то, что Code писал ответ в `CLAUDE.md`, а не в `.trio/`.

Это звучало правдоподобно и легло в основу нового явного правила протокола (§3 в `architecture.md`). Но когда позже в тот же день папку реально подключили и `CLAUDE.md` прочитали напрямую — оказалось, что файл **не менялся** и никакого отчёта Code там нет. Гипотеза не подтвердилась. Реальная причина старой нестыковки, скорее всего, была куда прозаичнее: чтение через прежний мост/путь показывало устаревшую кэшированную копию, а не путаница файлов.

**Важный урок сам по себе:** явное правило протокола осталось в силе, даже когда конкретный случай, который его мотивировал, не подтвердился — потому что риск такой путаницы («куда писать отчёт») реален независимо от того, произошла ли она именно в этот раз.

## GitHub-синхронизация: помогла с кодом, не помогла с `.trio/` — и по понятной причине

В тот же день пользователь подключил `Myrshefor/Finanon` (GitHub) как synced source к Claude-проекту. Cowork проверил через поиск по проекту: реальный код и доки репозитория (`frontend/src/...`, `package.json`, `README.md`, `docs/*.md`) действительно читаются — значимое расширение возможностей Chat, который раньше вообще не видел код напрямую.

Но целевые запросы на `.trio/STATUS.md`, `.trio/LEDGER.md` и хэш коммита `789b0a4` не дали вообще ничего. Когда папку подключили напрямую, выяснилась структурная причина: корень git-репозитория Finanon — `Разработка Finanon\Finanon`, а `.trio/` физически лежит на уровень выше (в `Разработка Finanon\`/`Claude\`). Он никогда не был частью репозитория, который синхронизируется с GitHub — поэтому и не мог найтись через поиск.

**Урок:** если файл не находится через синхронизацию, это не обязательно баг синхронизации — сначала проверь, действительно ли файл физически внутри синхронизируемого дерева.

## Разделение Finanon и trio (30.07, эта просьба)

После всего вышеперечисленного стало ясно: `.trio/` и `CLAUDE.md`, живущие в общей папке `Claude/` наравне с материалами Finanon, перемешивают историю разработки самого протокола с историей разработки приложения — и физически лежат не там, где логично для каждого из двух проектов. Пользователь попросил разделить:

- Finanon получает собственный `.trio/` и `CLAUDE.md` внутри своего настоящего git-репозитория.
- trio получает собственную среду разработки — этот репозиторий, `github.com/Myrshefor/.trio` — и начинает вести свою собственную историю (`STATUS.md`/`LEDGER.md` в его же корне), отдельно от Finanon.

Это и есть последняя запись в истории на момент написания этого документа.
