# trio-sync — сценарии обмена (v0.4.0)

Каноническое описание «кто с кем как говорит» — шесть сценариев обмена между тремя поверхностями, плюс граница, которую легко перепутать (`TO_CODE.md` vs device-bridge). `docs/architecture.md` описывает *что такое* каждый файл; этот документ — *через какой канал идёт каждый конкретный сценарий* и почему именно так.

Подготовлено Chat 2026-07-30 как черновик по итогам отдельного разговора с chyits, подтверждено и встроено в протокол Cowork в рамках апгрейда v0.4.0.

## 1. Три канала связи — общая картина

Только пара **Cowork ↔ Code** имеет прямой автоматический канал: файлы `TO_CODE.md`/`FROM_CODE.md`, которые обе стороны читают и пишут без участия человека на каждом шаге.

Обе пары с участием **Chat** всегда идут через пользователя:
- **Chat ↔ Cowork** — через зеркало в Claude Project (которое пишет только Cowork) и/или прямой пересказ пользователем.
- **Chat ↔ Code** — вообще без прямого канала, только через пользователя как мост.

Это не пробел, который нужно закрывать новым файлом — это архитектурная граница продукта (Chat не имеет доступа к файлам ни при каких настройках, см. `docs/architecture.md` §1), и протокол должен её учитывать, а не имитировать доступ, которого нет.

## 2. Шесть сценариев и оптимальный путь для каждого

### 2.1 Chat → Code (Chat нужен ответ Code)

**Путь:** Chat формулирует готовый текст вопроса (в формате записи `TO_CODE.md`, либо как прямой промпт для терминала). Пользователь вставляет это либо напрямую в сессию Code, либо просит Cowork внести в `TO_CODE.md` от имени Chat.

**Почему так:** Chat физически не может писать файлы — вставка всегда через пользователя. Cowork не обязателен как посредник, если вопрос простой и пользователь готов сам передать его Code напрямую.

### 2.2 Cowork → Chat («подумай с Chat»)

**Путь:** Cowork формулирует вопрос — либо прямо пользователю в разговоре (тот приносит его в чат с Chat как есть), либо пишет как документ в Claude Project, если хочет, чтобы Chat увидел его автоматически при следующем открытии проекта. Chat рассуждает в разговоре. Ответ обратно в Cowork несёт пользователь — либо вставляет ответ Chat, либо пересказывает вывод.

**Почему так:** это не задача на выполнение — файлы `TO_CODE.md`/`FROM_CODE.md` для этого не подходят по смыслу (они про хендофф исполнения на диске, не про сверку мышления). Если обмен содержательный, Cowork сам делает запись в `LEDGER.md` вида «Did: сверился с Chat по X, получил Y» — отдельный файл под это заводить избыточно при обычном объёме такого трафика.

### 2.3 Cowork → Code (задача для Code)

**Путь:** уже работает как есть — `TO_CODE.md` → Code читает → `FROM_CODE.md` → Cowork/пользователь видят. Первый реальный цикл уже пройден 2026-07-30. Менять нечего.

### 2.4 Chat → Cowork (Chat видит, что задача тяжёлая/долгая, предлагает Cowork)

**Путь:** Chat честно называет, что задаче нужен Cowork, а не пытается сделать вид, что справится сам. Пользователь переключается и приносит контекст в Cowork — либо переносом всего разговора (если внутри Project), либо явным пересказом/копией того, что Chat уже надумал.

### 2.5 Code → Chat (находка адресована лично Chat, не только Cowork)

**Путь:** Code технически пишет только в `FROM_CODE.md` — у него нет инструмента ни писать в Project, ни обращаться к Chat напрямую. Увидит ли это Chat — зависит от того, зеркалит ли Cowork файл в Project вовремя, либо пользователь сам приносит содержимое в разговор.

**Важно:** если Cowork долго не активен, Chat узнаёт об этом с задержкой — это ожидаемое поведение протокола, не баг.

### 2.6 Cowork читает файлы сам через device-bridge (не отдельная сессия Code)

**Разграничение:** `TO_CODE.md` — это про передачу **между сессиями** (Cowork закончил работу, вопрос ждёт, пока кто-то откроет отдельную сессию Code). Если у Cowork уже есть доступ к папке через device-bridge прямо сейчас, ему не нужно писать в `TO_CODE.md`, чтобы прочитать файл самому — это обычное чтение, не хендофф. `TO_CODE.md` нужен только тогда, когда ответ должен прийти именно от отдельной сессии Code.

**Практическое правило:** `TO_CODE.md` — только про то, что должен сделать или узнать Code. Если Cowork может закрыть вопрос своими средствами (device-bridge, инструмент Projects, веб) — использовать их напрямую, не создавать лишний виток через Code только чтобы «отметиться» в протоколе.

## Матрица направлений

| Откуда → Куда | Канал | Кто пишет | Кто читает |
|---|---|---|---|
| Cowork → Code | `TO_CODE.md` напрямую | Cowork | Code |
| Code → Cowork | `FROM_CODE.md` напрямую | Code | Cowork |
| Chat → Code | `TO_CODE.md`, пользователь как мост (Cowork может писать от имени Chat) | Chat формулирует, пользователь/Cowork записывает | Code |
| Code → Chat | `FROM_CODE.md` → зеркало `claude/trio-from-code-snapshot.md`, либо пользователь сам приносит содержимое | Code | Cowork зеркалит, Chat читает зеркало (с задержкой, если Cowork неактивен) |
| Cowork → Chat | Зеркала в Claude Project, либо пользователь приносит вопрос Cowork в разговор с Chat | Cowork | Chat — если разговор внутри Project, иначе через пользователя |
| Chat → Cowork | Пользователь переключается и приносит контекст (перенос разговора внутри Project, либо пересказ) | Chat формулирует, пользователь переносит | Cowork |

Из шести направлений только **Cowork ↔ Code** (первые две строки) — прямой автоматический канал. Остальные четыре — с участием Chat — всегда идут через пользователя как мост, потому что это архитектурная граница продукта (§1), не техническое ограничение, которое можно обойти файлом.

## Общее для всех шести

- Ничего из этого не заменяет собой пять файлов протокола (`docs/architecture.md` §2) — это описание маршрутов *между* ними, не новые файлы.
- Сценарии 2.1, 2.2, 2.4 и 2.5 (любой, где участвует Chat) требуют пользователя как моста или зеркала в Project — структурное ограничение, а не временное неудобство.
- Сценарии 2.3 и 2.6 (Cowork ↔ Code) — самые надёжные, потому что не зависят ни от Project, ни от посредника: оба читают/пишут `.trio/*.md` напрямую.
- Направление Cowork → Chat с v0.4.0 имеет два независимых механизма (зеркало + `CHAT_LINKS.md`, см. `docs/architecture.md` §5) — если один устарел или недоступен, есть второй.
