# duo-sync — архитектура (v0.5.0)

Полная спецификация протокола. Почему всё устроено именно так и какие инциденты к этому привели — `history-and-incidents.md`. Маршруты обмена — `scenarios.md`. Что изменилось относительно trio-sync v0.4.1 и как переносить старые проекты — `migration-v0.5.md`. Прежняя спецификация лежит без изменений в `docs/archive/v0.4.1/`.

## 1. Проблема и что изменилось

Две версии Claude, с которыми один человек работает над одним проектом, не видят разговоров друг друга:

- **Claude** — приложение Claude. С v0.5.0 это одна поверхность: раньше «Chat» и «Cowork» были разными, теперь это одно приложение с доступом к файлам (device-bridge, подключённый репозиторий, Project с синхронизацией GitHub), планировщиком задач и памятью.
- **Code** — сессия Claude Code в терминале. Shell и git на машине пользователя.

Главное ограничение, ради которого строился trio-sync v0.1–v0.4, — «Chat не видит файлов» — снято. Поэтому ушло всё, что существовало только ради него: зеркала в Project, `CHAT_LINKS.md`, ручной «мост через пользователя» и различие Chat/Cowork. Осталось то, что нужно любой паре сессий, которые не делят контекст: общая папка с текущим состоянием, адресные запросы и ответы, и дословный архив.

Имя папки `.trio/` сохранено намеренно: на него завязаны репозитории, `.gitignore`, `CLAUDE.md` проектов и скрипты синхронизации. Переименование — отдельная миграция, которую имеет смысл делать, только если мешает.

## 2. Файлы

| Файл | Тип | Кто пишет | Правило |
|---|---|---|---|
| `STATE.md` | живое состояние с тремя слотами | Claude, Code | ротация, ничего не теряется |
| `INBOX.md` | единый инбокс | оба | открытые + последние 2 закрытых |
| `DIALOGUE.md` | дословный архив закрытых обменов | оба, только дописывают | не тримится никем |
| `LEDGER.md` | переполнение `STATE.md` | оба, только дописывают | append-only |
| `DIALOGUE-archive-<год>.md` | ротация DIALOGUE | оба | как DIALOGUE |

### 2.1 STATE.md

Объединяет прежние `STATUS.md` (живой снэпшот) и краткие записи `LEDGER.md` (что произошло).

Три слота: `СЕЙЧАС`, `ПРОШЛАЯ ЗАПИСЬ`, `ПОЗАПРОШЛАЯ ЗАПИСЬ`. Каждый слот — один блок с заголовком `### <дата время> — <Claude|Code>` и полями **Фокус / Сделано / Решения / Открыто / Дальше**. Ниже — раздел `Постоянные требования`, который не ротируется.

Ротация (порядок важен — прерывание может породить дубль, но не потерю):

1. Содержимое `ПОЗАПРОШЛАЯ` (если есть) дословно уходит наверх `LEDGER.md`.
2. `ПРОШЛАЯ` → `ПОЗАПРОШЛАЯ`.
3. `СЕЙЧАС` → `ПРОШЛАЯ`.
4. Пишется новый `СЕЙЧАС`; всё, что осталось открытым в `Открыто` и не отмечено в `Дальше`, переносится вперёд (или явно закрывается).

Зачем три слота, а не один: нового сеанса почти всегда достаточно, чтобы понять, где остановились (`СЕЙЧАС`), что было до этого (`ПРОШЛАЯ`) и откуда это взялось (`ПОЗАПРОШЛАЯ`). Глубже — `LEDGER.md` по запросу. Файл остаётся коротким, а история не удаляется, а вытесняется вниз.

Правка своего же `СЕЙЧАС` в той же сессии и по тому же фокусу — на месте, без ротации. Ротируем при смене автора/сессии, фокуса или после завершённого куска работы.

Защита от «открытое потерялось»: пункт, который был в `Открыто`/`Дальше` и не закрыт, обязан перейти в новый `СЕЙЧАС`. Это правило введено вместо прежнего «если STATUS и LEDGER расходятся — прав LEDGER»: теперь они не два параллельных описания одного и того же, а один поток.

### 2.2 INBOX.md

Один файл вместо `TO_CODE.md` + `FROM_CODE.md`. Элемент — запрос и ответ вместе, с адресатом:

`### #<n> · <дата время> · <от> → <кому> · статус: open | answered`

- `open` — ждёт ответа адресата.
- `answered` — адресат ответил, ждёт, пока спросивший прочтёт и закроет.
- Закрывает спросивший: элемент уходит в `Закрыто — последняя`. Прежняя `последняя` сдвигается в `предпоследняя`, а прежняя `предпоследняя` **сначала** дословно дописывается наверх `DIALOGUE.md`, **потом** убирается из инбокса.

То же правило «два шага назад», что и в `STATE.md`: недавнее закрытое остаётся под рукой, дальше — в архив.

Конвенция `Resolved:` в `LEDGER.md` (v0.4.0) больше не нужна: факт закрытия виден прямо в `INBOX.md`, а дословный текст — в `DIALOGUE.md`.

Не создавать обмен ради обмена: если Claude может сам открыть файл, прочитать репозиторий или найти в вебе — он делает это сам. `INBOX.md` нужен для того, что может сделать или решить только другая поверхность, и для работы, которая должна пережить границу между сессиями.

### 2.3 DIALOGUE.md и ротация

Без изменений по смыслу: дословно, newest-first, никогда не сокращается и не пересказывается; очищает только пользователь по явной просьбе. Ротация при ~200 закрытых обменов или ~300 КБ: самый старый целый блок переносится без изменений в `DIALOGUE-archive-<год>.md`, под заголовком остаётся одна строка-ссылка. Запись в `DIALOGUE.md` теперь делает тот, кто закрывает элемент и вытесняет третий по давности (см. 2.2).

### 2.4 LEDGER.md

Теперь это только переполнение: сюда дословно попадает то, что вытеснено из `STATE.md`. Старые записи прежнего формата (`### дата — Chat/Cowork/Code`, `Resolved:`) остаются как есть; метки Chat и Cowork в них читать как «Claude».

## 3. `CLAUDE.md` — не часть протокола

Без изменений: `CLAUDE.md` — постоянные инструкции для Code, не канал обмена. Отчёты, ответы и находки — только в `.trio/`. Правило сохранено, хотя вызвавшая его гипотеза не подтвердилась (см. `history-and-incidents.md`): риск путаницы «куда писать отчёт» реален сам по себе.

## 4. Как Claude получает доступ к файлам проекта

Приложение Claude читает `.trio/` напрямую — не через зеркало:

1. device-bridge к папке проекта (если подключено приложение и выдан доступ к папке). Папку ищем сами: подключённые → листинг вероятных родителей (имена видны и без доступа) → запрос доступа к найденному пути → ввод пути пользователем только как последняя мера;
2. подключённый репозиторий (`add_repo`) или synced source Claude Project — для чтения;
3. если ничего этого нет — Claude честно говорит, что файлов не видит, и просит приложить `STATE.md` и `INBOX.md`.

Если `.trio/` проекта лежит вне git (как у Finanon, где она в `.gitignore` намеренно), через GitHub её не прочитать — нужен вариант 1.

## 5. Автоматизация: еженедельная ревизия

Опциональная задача по расписанию, читающая `.trio/` проектов и сообщающая о том, что залежалось: `СЕЙЧАС` старше 14 дней; открытые элементы `INBOX.md` старше 7 дней; `DIALOGUE.md` близко к порогу ротации; открытое, которое есть в `LEDGER.md`, но не в `STATE.md`; признаки хендоффа в `CLAUDE.md`; устаревшие файлы v0.4 рядом с `STATE.md`. Меняет только `INBOX.md` (добавляет элемент для того, кто должен разобраться).

## 6. Принципы

- Не удалять чужие записи `LEDGER.md` и `DIALOGUE.md`. `DIALOGUE.md` никогда не тримится.
- Файлы на диске — истина; `STATE.md` и `LEDGER.md` их описывают. При расхождении правим запись по диску.
- Один соблюдаемый канал лучше двух, один из которых не проверить. Побочных каналов (gist, заметки только в чате) нет.
- Протокол обходится файлами: ни сервисов, ни баз, ни запущенных процессов.
- Не делать вывод о потере данных, пока не проверил напрямую.
- Отсутствие файла в синхронизированном репозитории чаще про расположение папки относительно корня git, чем про сбой синхронизации.
- Старый скилл `trio-sync` рядом с `duo-sync` отключить, иначе сработают оба.
