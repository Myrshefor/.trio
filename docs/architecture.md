# trio-sync — архитектура (v0.4.0)

Полная техническая спецификация протокола. Для истории решений и разбора реальных инцидентов, которые привели к этой архитектуре, см. `history-and-incidents.md`. Для разбора конкретных сценариев обмена «кто с кем как говорит» (шесть направлений + границы каналов) — см. `scenarios.md`.

## 1. Проблема

Три поверхности Claude, с которыми работает один человек над одним проектом, не делятся контекстом между собой:

- **Chat** — обычная переписка на claude.ai/desktop. Не имеет доступа к файлам или устройству пользователя вообще — это жёсткое ограничение продукта, не настройка прав.
- **Code** — сессия Claude Code в терминале. Прямой shell/git-доступ к файлам проекта на машине пользователя.
- **Cowork** — автономный агент в песочнице или desktop-режиме. Доступ к файлам пользователя — через device-bridge, когда пользователь подключил папку; плюс отдельный инструмент для чтения/записи в Claude Projects.

Без общего механизма каждая поверхность начинает с нуля, даже продолжая работу, начатую другой — пользователю приходится каждый раз пересказывать контекст заново.

## 2. Решение: `.trio/` — общая папка внутри проекта

Пять markdown-файлов внутри проекта, которые все три поверхности читают перед началом работы и обновляют после значимого шага. Никаких внешних сервисов, баз данных или процессов — просто файлы, которые уже есть в любой файловой системе или git-репозитории. Ротация `DIALOGUE.md` (см. ниже) может со временем породить дополнительные `DIALOGUE-archive-<год>.md`, а видимость для Chat через GitHub (§5) — необязательный `CHAT_LINKS.md`; оба — сателлиты этих пяти файлов, не замена им.

| Файл | Тип | Кто читает | Кто пишет |
|---|---|---|---|
| `STATUS.md` | живой снэпшот | Code, Cowork (напрямую); Chat — только через зеркало в Claude Project | Code, Cowork — перезаписывают на месте |
| `LEDGER.md` | append-only лог | Code, Cowork | Code, Cowork — только добавляют запись сверху, никогда не удаляют чужие |
| `TO_CODE.md` | инбокс, входящее для Code | Code | Cowork/Chat (Cowork пишет от имени Chat, у которого нет доступа к файлам) |
| `FROM_CODE.md` | инбокс, входящее для Cowork/Chat | Cowork (и через зеркало — Chat) | Code |
| `DIALOGUE.md` | permanent verbatim | Code, Cowork; Chat — через зеркало | обе стороны, только добавляют, никогда не тримят |

### STATUS.md

Живой снэпшот: текущий фокус, недавние решения, открытые вопросы, next actions. **Перезаписывается на месте — это не история**, старые версии не сохраняются (кроме того, что попало в `LEDGER.md`).

### LEDGER.md

Append-only, новые записи — в начале файла, сразу под заголовком. Формат записи:

```markdown
---
### <дата> <время> — <Chat|Code|Cowork>
**Did:** <1–3 предложения>
**Touched:** <пути файлов, если есть — иначе пропустить строку>
**Handoff:** <что должны знать/сделать остальные два — иначе пропустить строку>
---
```

Записи короткие — по правилу, «несколько строк, не стенограмма». Полный дословный текст переписки в LEDGER не попадает никогда by design — для этого есть `DIALOGUE.md`.

### TO_CODE.md / FROM_CODE.md — направленные инбоксы

Введены в v0.3.0 вместо (точнее, в дополнение к) свободного поля `Handoff:` внутри записей LEDGER. Раньше адресация «кто кому что сказал» кодировалась текстом внутри общей записи — работало, но не давало чёткого «вот файл, который Code обязан прочитать, вот файл, который обязан прочитать я», с понятным «прочитано / не прочитано».

- `TO_CODE.md` — Cowork или Chat пишут явный вопрос/поручение для Code. Chat не может писать файлы напрямую — Cowork пишет от его имени, либо пользователь передаёт формулировку сам.
- `FROM_CODE.md` — Code пишет явный ответ обратно.
- Оба файла — **инбоксы, не история**: как только пункт обработан (Code ответил / Cowork-и-Chat увидели ответ), запись из соответствующего файла убирается — но её полный текст перед этим переносится в `DIALOGUE.md` (см. ниже), так что ничего не теряется, просто перестаёт быть «открытым».

#### Конвенция «resolved» (введено в v0.4.0)

Раньше правило было устным — «убери запись, когда обработано». Оно остаётся в силе, но дополнено обязательным шагом: сторона, которая закрывает обмен (переносит вопрос+ответ в `DIALOGUE.md` и убирает записи из `TO_CODE.md`/`FROM_CODE.md`), обязательно добавляет строку в `LEDGER.md` — отдельной короткой записью или строкой внутри более крупной записи той же сессии, любой вариант допустим, лишь бы строка появилась:

```
Resolved: <дата закрытия> — <кто закрыл: Code|Cowork|Chat> — см. DIALOGUE.md (<дата исходной записи>)
```

Смысл: раньше по `LEDGER.md` нельзя было быстро понять, что именно из TO_CODE/FROM_CODE закрыто и когда, не сверяясь отдельно с `DIALOGUE.md`. Теперь это видно прямо в ленте `LEDGER.md`, одной строкой — само содержание обмена по-прежнему только в `DIALOGUE.md`.

### DIALOGUE.md — «хот-память»

Единственный файл в протоколе, который **никогда не тримится и не редактируется задним числом** — только дописывается сверху (newest-first, как LEDGER). Полный, дословный текст того, что стороны реально сказали друг другу через `TO_CODE.md`/`FROM_CODE.md` — не заметки «Did/Touched», а сама формулировка вопроса и сама формулировка ответа. Очищается только по явной просьбе пользователя — никакая автоматика (ни Code, ни Cowork) не имеет права его тримить.

Мотивация: `STATUS.md` перезаписывается, `LEDGER.md` обязан быть кратким — значит нигде в протоколе не было места, куда попадал бы полный текст переписки в неизменном виде, к которому пользователь мог бы быстро вернуться, не поднимая заново текущий контекст разговора.

#### Лимит объёма и ротация (введено в v0.4.0)

«Никогда не тримится» значит, что содержимое никогда не удаляется и не сокращается — это не то же самое, что «файл неограниченного размера». Решение: ротация целыми блоками, а не тримминг.

- **Порог:** 200 разрешённых обменов (записей, перенесённых из TO_CODE/FROM_CODE) **или** ~300 КБ размера файла — что наступит раньше. Число выбрано Cowork как разумный дефолт, не требующий отдельного согласования с chyits; при желании его можно поменять — это не архитектурное решение, а настраиваемый параметр.
- **По достижении порога:** самый старый блок (запись целиком, от `---` до `---`) вырезается из `DIALOGUE.md` целиком, без изменений, и переносится в `DIALOGUE-archive-<год>.md` — новый файл рядом с остальными файлами протокола (в `.trio/`, либо в корне репозитория для этого самого репозитория). Архив подчиняется тем же правилам, что сам `DIALOGUE.md`: append-only, newest-first, никогда не тримится, чистится только по явной просьбе пользователя.
- **В `DIALOGUE.md`, сразу под заголовком, остаётся одна строка-ссылка:** `_Архив старше <дата самой ранней оставшейся записи> — см. DIALOGUE-archive-<год>.md._` — так видно, что часть истории вынесена, и куда именно.
- Порог проверяет тот, кто дописывает новую запись (Code или Cowork), после дописывания — прежде чем считать работу завершённой.
- Год для имени архива — год самой старой записи в переносимом блоке.

## 3. `CLAUDE.md` — не часть протокола

`CLAUDE.md` (или любой другой файл персистентных инструкций, который Claude Code читает при старте) **не входит** в trio-handoff. Он хранит постоянные инструкции для Code, а не сообщения между поверхностями. Если Code отвечает на вопрос, отчитывается о находке или логирует работу — это идёт в `.trio/LEDGER.md` (плюс `FROM_CODE.md`/`DIALOGUE.md`, если это ответ на конкретный вопрос из `TO_CODE.md`) — никогда в `CLAUDE.md`. Это правило появилось как защита от конкретной спутанности (см. `history-and-incidents.md`) — гипотеза не подтвердилась при проверке, но риск такой путаницы реален, поэтому правило осталось явным.

## 4. Зеркалирование в Claude Project (для Chat)

Обычный Chat не имеет доступа к файлам ни при каких настройках прав — это архитектурное ограничение продукта. Единственный канал, который Chat получает автоматически — Claude Projects: документы прикреплённого проекта подтягиваются в контекст сами, без ручной вставки, если разговор идёт именно внутри этого проекта.

Если к сессии Cowork прикреплён Claude Project:

1. После реальной (не read-only) работы над `STATUS.md` — Cowork также пишет зеркало в проект, например `claude/trio-status-snapshot.md`.
2. Когда в `FROM_CODE.md` появляются открытые пункты — Cowork зеркалит его тоже, например `claude/trio-from-code-snapshot.md`.
3. Когда в `DIALOGUE.md` появляются новые записи — Cowork дописывает их (только новое, не весь файл каждый раз) в `claude/trio-dialogue-mirror.md` — этот мираж должен оставаться дословным и кумулятивным, как и источник, никогда не тримиться.
4. Каждое зеркало помечается временем и автором последней синхронизации.
5. Code и Chat не имеют инструмента Projects — это шаг только для Cowork.

## 5. Видимость для Chat через публичный GitHub (введено в v0.4.0)

### Проблема

Зеркалирование в Claude Project (§4) — единственный автоматический канал для Chat, но требует, чтобы Cowork был активен, не забыл синхронизировать, и чтобы разговор шёл именно внутри подключённого Project. Между синками зеркало может устареть.

### Второй канал — и его реальное ограничение

Если `.trio/` (или, как в этом самом репозитории, весь его корень) лежит в **публичном** GitHub-репозитории, обычный Chat может прочитать конкретный файл через веб-поиск/фетч — **но только если точная прямая ссылка на этот файл уже присутствует текстом в разговоре** (её напечатал человек, вернул поиск, или она пришла из документа Project Knowledge, подтянутого в контекст автоматически). Chat **не может** сам обойти дерево репозитория и **не может** достроить ссылку на файл, зная только ссылку на корень репозитория — это ограничение продукта, а не временная неполадка, и оно проверено вживую.

### Решение: файл-указатель `CHAT_LINKS.md`

Небольшой файл со списком прямых ссылок на все ключевые файлы репозитория, одна строка на файл, формат:

```
<repo_url>/blob/<branch>/<путь>/<файл>
```

Покрывает пять файлов протокола (`STATUS.md`, `LEDGER.md`, `TO_CODE.md`, `FROM_CODE.md`, `DIALOGUE.md`, плюс `DIALOGUE-archive-*.md`, если уже есть), всё содержимое `docs/*.md`, и сам `CHAT_LINKS.md`. Расположение на диске: `.trio/CHAT_LINKS.md` (в этом репозитории — `CHAT_LINKS.md` в корне, как и остальные файлы протокола, см. `HANDOFF.md` → «Особенность этого репозитория»).

### Доставка в Claude Project — по приоритету

Файл на диске сам по себе бесполезен для Chat, пока не окажется в контексте разговора — единственный надёжный канал для этого по-прежнему Project Knowledge (§4). Два способа доставить, по приоритету:

1. **Если к текущей сессии Cowork подключён нужный Claude Project** — Cowork пишет `CHAT_LINKS.md` напрямую в Project (например, `claude/trio-chat-links.md`) через инструмент Projects — так же, как уже пишет зеркала статуса/диалога из §4. chyits ничего не загружает вручную.
2. **Если Project не подключён к текущей сессии** — Cowork генерирует содержимое файла и прямо просит chyits положить его в Project Knowledge нужного проекта — разовая ручная загрузка.

### Соотношение со старым зеркалированием (§4)

Дополняет, а не заменяет. Зеркала `claude/trio-status-snapshot.md` / `trio-from-code-snapshot.md` / `trio-dialogue-mirror.md` — снэпшот содержимого на момент последней синхронизации Cowork; работает даже без GitHub, но может устареть между сессиями Cowork. `CHAT_LINKS.md` — маленький, редко меняется (только когда меняется сам набор файлов, а не их содержимое), но даёт Chat возможность запросить у веб-инструмента **живую, самую свежую** версию любого конкретного файла по прямой ссылке — а не то, что Cowork успел когда-то скопировать в зеркало.

### Шаг настройки нового проекта (см. `SKILL.md` → «Если `.trio/` не существует ещё»)

1. Спросить chyits, будет ли у проекта публичный GitHub-репозиторий для `.trio/` (если да — дать ссылку, либо создать репозиторий на этом же шаге).
2. Если да — сгенерировать `.trio/CHAT_LINKS.md` по шаблону выше, с реальными путями файлов этого проекта.
3. Доставить в Claude Project по приоритету из раздела выше.
4. Если GitHub пока нет — зафиксировать это как открытый пункт в `STATUS.md` («видимость Chat ограничена ручной вставкой + зеркалом Cowork»), не блокировать остальную настройку.
5. Если позже репозиторий появляется, а `CHAT_LINKS.md` — нет, любая поверхность, заметившая это, предлагает донастроить, а не оставляет молча.

## 6. Роли и идентификация

Перед чтением/записью нужно понять, какая ты поверхность — записи в LEDGER помечаются ролью автора:

- **Code** — прямой shell/git-доступ на машине пользователя (сессия Claude Code в терминале).
- **Cowork** — автономный агент, работающий с файлами/вебом/инструментами в песочнице или desktop-задаче, без пошагового руководства человеком.
- **Chat** — живая переписка с пользователем, обычно без прямого доступа к файлам или с ограниченным доступом.

Если неоднозначно — лучше спросить пользователя один раз, чем угадать неправильно.

## 7. Общие принципы

- Не удалять чужие записи `LEDGER.md`/`DIALOGUE.md` — обе истории общие. `LEDGER.md` можно тримить собственному автору, если запись реально устарела; `DIALOGUE.md` — никогда, только по явной просьбе пользователя.
- `TO_CODE.md`/`FROM_CODE.md` — наоборот, предполагают удаление обработанных пунктов, это инбоксы, а не история. При удалении — не забыть строку `Resolved:` в `LEDGER.md` (§2).
- Если `STATUS.md` и `LEDGER.md` расходятся — `LEDGER.md` источник истины; поправь `STATUS.md`.
- Если `.trio/*.md` и `CLAUDE.md` расходятся о том, что сообщил Code — `.trio/*.md` источник истины для целей trio-sync; `CLAUDE.md` никогда не должен был нести эту информацию.
- Протокол работает только если все три поверхности реально его используют — если кто-то «не увидел» что-то, первым делом проверь, что trio-sync установлен и там тоже, и что запись попала именно в `.trio/*.md`, а не в другой файл.
- `DIALOGUE-archive-<год>.md`, порождённый ротацией (§2), живёт по тем же правилам, что сам `DIALOGUE.md` — append-only, никогда не тримится никем, кроме явной просьбы пользователя.
- `CHAT_LINKS.md` (§5) необязателен — это дополнительный канал видимости для Chat, а не часть минимального протокола. Репозиторий приватный или GitHub не используется — протокол работает и без него, только через зеркалирование (§4).
- Если `CHAT_LINKS.md` существует, но набор файлов в репозитории с тех пор изменился (новый файл в `docs/`, переименование, появился `DIALOGUE-archive-*.md`) — тот, кто это заметил, обновляет `CHAT_LINKS.md` и его зеркало в Project, а не оставляет ссылки битыми.
